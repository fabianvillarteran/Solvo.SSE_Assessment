# Decisions

## Where the spec was unclear, contradictory, or silent

- **§3.2 vs §3.5/§4 — attachment dedup scope.** §3.2 says "two attachments are duplicates if they have the same sha256," read globally. §3.5 requires families to come out intact, and §4 requires each custodian's set to be self-contained. Taken literally, §3.2 breaks both: `batch-sample.json` has `Q3-budget.xlsx` and `vendor-report.pdf` each attached to two different emails for two different custodians, with identical bytes. Global hash dedup keeps whichever copy is seen first and silently drops the attachment from every other family that also had it — which is exactly INGEST-4471 ("emails arriving in review without their attachments").
  I decided §3.5/§4 win: an attachment is only a duplicate of another attachment *within the same family* (same top-level parent). A genuine duplicate attached twice to the *same* email is still suppressed per §3.2. I did not ask and made the call, because the sample data and the ticket both point at the same conclusion and the fix is narrow. I'd flag this decision explicitly on a PR rather than assume it's uncontroversial — a reasonable alternative reading is "attachments dedup globally, and that's a conscious storage-savings tradeoff reviewers are told about separately," which I think is a worse reading given §3.5's wording ("a reviewer who opens an email must see every attachment"), but it's a product call, not just a technical one.
- **Loose files vs §4.** The same tension exists for loose files: `policy.docx` appears for both `jsmith` and `mlee` with identical bytes, and the one global copy kept could belong to either custodian. §3.1 says loose files dedup globally, full stop, with no family concept to loosen the scope the way §3.5 did for attachments. I left loose-file dedup global/unscoped, per §3.1 as written, but that does mean a custodian severed from the matter per §4 could be missing a loose file that only survived in the output because it was collected from someone else's share too. I'm flagging this rather than silently deciding it's fine — it's the same shape of problem as the attachment bug, just not the one the ticket named, and not one I felt confident resolving unilaterally since it requires either (a) keeping one copy per custodian instead of one copy per batch (more rows, contradicts "duplicates are omitted" in §3.6 if read strictly), or (b) accepting the gap. I'd ask about this one rather than guess further.
- **§3.3 vs §4 — cross-mailbox email dedup makes the custodian-completeness tension worse, not just present.** Once §3.3 is implemented, `DOC-000001` (jsmith's Sent Items copy) and `DOC-000009` (mlee's Inbox copy of the same email) collapse into one row under `jsmith` — `mlee`'s production now has *no* row for that email at all, and loses its attachments with it (they were byte-identical to jsmith's copies, so they collapse too once the families merge). This is the same §3.2/§3.5-vs-§4 shape as the attachment decision above, but for whole emails, and it's more visible: a reviewer looking at only mlee's production would see an email thread with a reply (`DOC-000012`, "Re: Q3 budget review") but not the email it's replying to. The load-file schema only has one `Custodian` column (not a list), so there's no way to say "this surviving row also belongs to mlee" within the fixed format — which pushed me toward implementing §3.3 literally (global, whichever mailbox's copy has the lexicographically smaller DocId survives) and documenting the gap rather than inventing an extra column the ingest job doesn't expect. I'd ask whether custodian-complete productions are actually generated from a separate, per-custodian dedup pass downstream (common in e-discovery tooling) before accepting this as a real gap versus an expected two-stage pipeline.
- **Survivor selection and determinism (§6.1).** The original code kept "whichever duplicate is encountered first" by input order, which fails §6.1 outright: reordering `batch.Documents` changes which copy's `Custodian`/`FileName` survives. I made survivor selection deterministic by picking the lexicographically smallest `DocId` within each duplicate group (hash-based or logical-content-based), independent of array order. I verified this against `batch-sample.json` directly (shuffled input, diffed output byte-for-byte) in addition to a unit test. Not stated anywhere in the spec which copy *should* win when it matters (e.g. which custodian's `FileName` spelling survives) — I chose DocId order only for determinism's sake, not because it's semantically meaningful; a real system would probably want an explicit tie-break rule (earliest `sentDate`, or a custodian priority list) instead.

## What I changed and why

- **`Deduper.cs` — scoped attachment dedup to `(familyId, sha256)` instead of global `sha256`.** Fixes INGEST-4471. Emails and loose files still dedup on bare `sha256` across the whole batch, matching §3.1 and current (unchanged) behavior for emails.
- **`Deduper.cs` — added `FormatSentDateUtc`, applied to both an email's own `SentDate` and the date an attachment inherits from its parent.** The tool was passing the raw header value straight through (e.g. `2024-03-05T14:22:00-05:00`) into the load file, which §5 requires as UTC `YYYY-MM-DDTHH:MM:SSZ`. This wasn't in the ticket but was visible in `current-tool-output.csv` once I looked — every email's `SentDate` in that file carries a non-`Z` offset. Converts via `DateTimeOffset.Parse` → `.UtcDateTime`, formatted with a fixed pattern that also drops fractional seconds, which the spec calls out explicitly as not allowed.
- **`Deduper.cs` — implemented §3.3 (cross-mailbox email dedup).** Two emails are the same logical message if `From`/`To` match case-insensitively, `Subject` and the UTC-normalized `SentDate` match exactly, and `Body` matches after normalizing line endings (`\r\n`/`\r` → `\n`) and trimming. This is deliberately narrower than "same subject and date" — `EmailsWithDifferentBody_AreNotMergedAsDuplicates` guards against that — and deliberately tolerant of exactly the three things the spec says vary by mailbox (§3.3: "headers, encodings, and line endings"). When a duplicate email is suppressed, its attachments are re-parented onto the surviving email's `FamilyId`/`ParentId` rather than left pointing at a row that no longer exists; if that re-parenting makes an attachment a same-family duplicate of the surviving email's own attachment (the common case — attachments usually survive mailbox transit unmangled, unlike headers), it's suppressed too, via the existing §3.2 family-scoped logic.
- **`Deduper.cs` — reworked duplicate-survivor selection to be deterministic (§6.1).** Replaced "first one seen in iteration order wins" with "lexicographically smallest DocId in the duplicate group wins," computed via grouping rather than a single streaming pass. This was necessary groundwork for §3.3 (can't resolve which email survives, and therefore where an orphaned attachment re-parents, without first grouping all of them) but also fixes a latent order-dependence bug that applied to the original attachment/loose dedup too.
- **Tests added in `DeduperTests.cs`** (TDD — written failing before each fix): `CrossFamilyDuplicateAttachment_BothFamiliesKeepTheirCopy`, `SameFamilyDuplicateAttachment_IsStillSuppressed`, `SentDate_IsConvertedToUtcZFormat`, `SentDate_DropsFractionalSeconds`, `SentDate_AttachmentInheritsConvertedUtcDate`, `CrossMailboxDuplicateEmail_SecondCopyIsSuppressed`, `CrossMailboxDuplicateEmail_SurvivorIsIndependentOfInputOrder`, `EmailsWithDifferentBody_AreNotMergedAsDuplicates`, `CrossMailboxDuplicateEmail_AttachmentsCollapseIntoSurvivingFamily`.

## What I didn't get to

- The loose-file/§4 and email/§4 custodian-completeness gaps described above — flagged, not resolved.
- `EmailContentKey`'s matching rule (exact `Subject`/body-after-normalization, case-insensitive addresses) is a judgment call, not something the spec pins down precisely. It's untested against messier real-world variation the spec doesn't mention — e.g. a mail client that rewraps body text at a different column width, or appends a mailbox-specific disclaimer/signature on receipt — either of which would make a real duplicate fail to match under my rule. The spec's own examples (headers, encoding, line endings) are all things my key already tolerates; anything beyond that is me extrapolating.
- `FamilyId`/inherited `SentDate` (and now, email-survivor resolution for re-parenting) are resolved one `parentId` hop up, same as the original code. The spec says an attachment can itself have attachments (email-within-email), so a two-hop chain would currently get the *intermediate* document's id as `FamilyId` instead of walking to the true top-level ancestor. Not covered by the sample batch, not tested, not fixed — flagging it since §2's data model explicitly allows it.
- Haven't tested behavior at the stated upper bound (~2M documents, §6.2) for performance/memory. Current implementation is O(n) (dictionary lookups + grouping), which should hold up, but I haven't measured it, and `GroupBy` + LINQ allocate more intermediate collections than the original single-pass loop did — worth a benchmark before trusting it at 2M rows.
- No test exercises a three-mailbox copy of the same email (sender's Sent Items + two recipients' Inboxes) — only the two-mailbox case the sample data has.

## What I'd do next

- Get an answer on the custodian-completeness questions above rather than guessing further — specifically whether a separate per-custodian production pass exists downstream of this tool.
- Add a test for the multi-hop attachment family/date/re-parenting resolution, and fix it if the spec intends nested chains to bubble all the way to the top-level email (I believe it does, based on "every attachment that was on it" in §3.5).
- Benchmark against a generated ~2M-document batch to sanity-check §6.2 before trusting the LINQ-heavy rewrite at that scale.
- Pressure-test `EmailContentKey` against messier variation (rewrapped body text, appended disclaimers) and decide, with input from the team, whether to tolerate more than the spec's three named causes of byte divergence.

## Working with the AI

- Used the AI primarily for two things: cross-checking the README's claims against the actual spec/code/sample-data (it found the real `sha256` collisions in `batch-sample.json` that explain the ticket, which is what let me pin the attachment-dedup decision above on evidence rather than a guess), and TDD — writing failing tests before touching `Deduper.cs`.
- Had to supply the actual design decision myself (§3.2 vs §3.5/§4 scope) — the AI surfaced the contradiction clearly but a call on which section should win is a product/spec judgment, not something to delegate.
- I'd warn a teammate: the AI will converge on the first consistent interpretation it finds and implement it fluently, which makes a wrong-but-plausible reading of an ambiguous spec section easy to miss if you don't independently check the sample data yourself the way I did here.
- Caught by review, not by me noticing proactively: when implementing the §3.3 content key, the AI's edit silently wrote an invisible control byte (0x01) into `Deduper.cs` as a string separator instead of the visible `` escape sequence it intended — it rendered as nothing in `grep`/file-read output, so it looked identical to an empty-string separator. It was functionally harmless here (the tests still passed), but it's the kind of thing that could sit in a file unnoticed and cause strange behavior if a future edit assumed the string was really empty, or if an editor/linter mangled the raw byte. Worth a second look any time an AI-driven edit to a string literal doesn't visually match what you'd expect, even if the diff appears to apply cleanly.
- After implementing §3.3, re-ran the actual tool (not just unit tests) against `batch-sample.json`, and separately against a shuffled copy of the same file, diffing the two outputs byte-for-byte to confirm §6.1 order-independence end-to-end — the unit test alone covers the logic in isolation but doesn't prove the full pipeline (JSON parsing → dedup → CSV writing) is order-stable.
